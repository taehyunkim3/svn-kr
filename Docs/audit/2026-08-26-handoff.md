## 커밋 화면 작업 (2026-08-27)

사용자가 실제 화면을 보고 요청한 것들이다. 전부 머지됐다.

- **커밋 확인 창** — 본문 문구 교체, 체크박스 뜻을 알리는 안내 추가(`ui.commit.restoreSelectionHelp`),
  `아니오`→`취소`, `확인`→`커밋 진행`. 취소 버튼의 `.defaultAction`을 떼서 파란 버튼은 하나만 남았다.
  **서버 삭제가 있을 때 Return은 아무 것도 실행하지 않는다.** Escape만 취소다. 이 안전장치를 되돌리지 마라
  (`Tests/SVNMacTests/DestructiveReturnKeyTests.swift`가 취소 버튼 블록에 `.defaultAction`이 없음을 단정한다).
- **커밋 중 조작 잠금** — `ProjectStore.isCommitInteractionLocked`
  = `isSelectedProjectActionBlocked || isCommittingSelectedProject`. 커밋 중 잠금을 더하면서 기존 차단
  조건을 유지한다. 처음 제출은 `isCommittingSelectedProject`만 봐서 새로고침·업데이트 미리보기 중에도
  커밋이 눌리는 회귀를 냈다. 반려하고 고쳤다. **이 속성을 단순화하지 마라.**
- **커밋 실시간 로그** — `SVNClient.commit`에 `progress:`(기본 nil) 추가. 체크아웃과 같은 배관
  (`SVNOutputProgressReader` → `CheckoutProgressBuffer`)을 쓴다. `add --parents` 단계 출력도 흐른다.
  세션 ID로 늦게 온 출력을 버리고, 실패한 커밋의 로그는 남긴다.

## 미추적 폴더 하위 선택 (2026-08-27)

커밋이 오래 걸리는 원인이었다. 폴더를 체크하면 `add`의 기본 depth가 infinity라 하위 전체가 올라갔다.

- `SVNClient.untrackedChildren(at:directory:credentials:)` — **직속 항목만** 낸다. 재귀 금지.
  무시된 항목도 표시를 달아 함께 낸다. 반환형 `SVNUntrackedChild`(`Sources/SVNCore/Models.swift:341`).
- 커밋 경로 계산이 바뀌었다. 새로 추가되는 상위 폴더는 커밋 대상에 **반드시 들어가야 한다**
  (없으면 `E200009`). 그래서 상위 폴더 주입이 필요한 커밋에서만 `svn commit --depth empty`를 쓰고,
  사용자가 폴더 자체를 골랐을 때는 그 하위 항목을 스냅샷으로 다시 읽어 명시 경로로 펼쳐 넘긴다.
  `--depth`는 호출 단위 옵션이라 대상별로 다르게 줄 수 없기 때문이다.
  **이 구조를 단순화하려면 `Tests/SVNCoreTests/SVNUntrackedChildrenIntegrationTests.swift`의 세 시나리오를
  먼저 읽어라.** 이전에 추가 예약된 형제가 함께 올라가지 않는 것까지 실 svn으로 고정돼 있다.
- 선택 규칙(UI): 폴더 체크 = 하위 전체, 하위 개별 체크 = 그 항목만, **둘은 상호배타**.
  커밋 대상은 `selectedCommitPaths() = selectedPaths ∪ selectedUntrackedChildPaths` 한 곳에서 계산한다.
- 지연 로딩: 펼칠 때 한 단계만 읽고 캐시한다. 새로고침하면 `untrackedChildrenRefreshGeneration`을
  올려 캐시와 하위 선택을 버린다. 오래된 목록으로 사라진 파일을 커밋 대상에 넣는 것을 막는다.
- 무시는 새로 만들지 않았다. 하위 행이 기존 컨텍스트 메뉴(`ui.ignore.item` / `ui.ignore.fileExtension`)를
  그대로 쓴다.

## 실사용에서 나온 결함 2건 (2026-08-27, 둘 다 수정 머지됨)

- **미추적 폴더를 다시 접을 수 없었다.** `visibleUntrackedDescendants(in:)`가 시작 디렉터리의 펼침
  상태를 보지 않고 캐시를 그렸다. 하위 폴더는 확인하면서 최상위만 빠져 있었다. 한 줄 가드로 고쳤고
  테스트가 4단계를 고정한다(펼침 → 중첩 펼침 → 접기 → 다시 펼쳤을 때 중첩 상태 보존).

- **트리 충돌이 NFC/NFD 별칭 뒤에 가려졌다.** 사용자 저장소에서 나온 실제 상태다.
  ```
  ?       .../KOFA2_DE301_프로그램 목록(AMS_정보병합)_v0.1.xlsx      (NFD 실물)
  !     C .../KOFA2_DE301_프로그램 목록(AMS_정보병합)_v0.1.xlsx      (NFC 등록본, 트리 충돌)
        >   local file edit, incoming file delete or move upon update
  ```
  화면에는 `미추적` 하나만 떴고, Finder에서 실물을 지워야 충돌이 드러났다.
  원인은 `SVNWorkingCopySnapshot.visibleStatuses`가 `treeConflicted`를 보지 않은 것이다.
  `status == "normal"`이면 버렸다. 조건에 `entry.treeConflicted`를 더해 고쳤다.

### 이 수정이 어제 결론을 뒤집는다 — 반드시 함께 읽어라
`Docs/audit/2026-08-26-recovery-reachability-repro.md`는 「제자리 정리 불가인데 복구는 가능한」 경우가
실재한다고 결론지었다. 그 근거가 **바로 이 숨겨진 트리 충돌**이었다. 충돌이 표시 상태에서 빠져 있어
복구 미리보기가 차단하지 않았던 것이다.

지금은 충돌이 보이고 복구 미리보기가 그 경로를 차단한다. 계약을 고정한 테스트도 이름과 단정이 바뀌었다.
`realSVNUnrepairableCanonicalAliasCanHaveUnblockedRecovery` →
`realSVNNormalTreeConflictIsVisibleAndBlocksRecovery`
(`Tests/SVNCoreTests/SVNWorkingCopyRecoveryReachabilityTests.swift`).

**새 작업 폴더 복구 진입점은 유지한다.** 되돌리지 마라. 사용자가 밟는 순서가 이렇게 정리됐다.
1. 충돌이 화면에 보인다 → 충돌 해결 화면에서 처리한다
2. 그 뒤 제자리 정리 또는 새 작업 폴더 복구를 쓴다
버튼을 눌러도 미리보기가 차단 경로를 보여주므로 왜 못 하는지가 드러난다. 이전처럼 단서 없이 막히지 않는다.
